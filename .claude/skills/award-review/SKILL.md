# award-review - 站在得獎門檻回頭看

## 概述

多數專案已有「怎麼做設計」的指引（例如 frontend-design 類 skill）與「畫面有沒有壞」的驗收流程。這個 skill 補第三個視角：**評審**。「以得獎程度為目標」這句話本身不是知識，評審怎麼看、哪裡會扣分、先修哪個，才是要外化的東西。沒有它，AI 會給出「加點動畫、換個字體」這種泛用建議；有了它，建議會附截圖證據、對應評審維度，並排成可執行的分階段計劃。

這份 skill 不綁定專案：技術棧、框架、驗證工具都由目標專案決定，這裡只定義評審視角與輸出格式。

## 核心原則

| 原則 | 為什麼 | 對比 |
|------|--------|------|
| **先看再評** | 評審看的是畫面，不是程式碼。沒截圖的意見是猜的 | ❌ 讀原始碼就下結論 → ✅ 實際開頁、桌機與手機各截一輪再評 |
| **十秒辨識** | awwwards 評審在首屏十秒內決定印象。問「遮掉 logo，還認得出是這個站嗎」 | ❌ 左文右圖加兩顆按鈕的通用 hero → ✅ 只有這個主題才會這樣做的簽名時刻 |
| **動態要有目的** | 動態是敘事工具不是裝飾。每段都逐段 fade-up 等於沒有設計 | ❌ 每個區塊都滑入淡入 → ✅ 一段精心編排的開場，其餘只回應使用者動作 |
| **字體帶性格** | 字體是頁面的聲音。安全牌沒有錯，但拿不到 Design 分 | ❌ 只靠字重區分層級 → ✅ 展示字只用在關鍵位置，與內文形成明確對比 |
| **內容是真的** | Webby 的 Content 與 Functionality 各佔一個維度；空殼再美也不會得獎 | ❌ 假數據、占位文案 → ✅ 真實可用、量足、文案前後一致 |
| **細節無瑕** | 評審會放大看：斷句切詞、文案矛盾、emoji 當圖示、孤卡、對比不足。最便宜也最常被扣的分 | ❌ 「小問題之後再說」 → ✅ 列成 P0 先修 |
| **大膽只花在一處** | 得獎站有一個讓人記住的時刻，其餘安靜有紀律。到處大膽等於到處吵 | ❌ 每區都有特效 → ✅ 押注一個簽名時刻，其他收斂 |

## 審查流程

1. **建立基準**：用專案可用的瀏覽器工具（Playwright MCP、Claude in Chrome 等）實際開啟頁面；目標專案若有自己的 UI 驗收 skill 或啟動流程，先依它建置與啟動。桌機約 1440 寬與手機約 390 寬各截首屏、全頁與關鍵互動狀態；動態要等它跑完再截。沒有任何瀏覽器工具時，明確告知這次審查只根據原始碼與素材，結論可信度較低。
2. **十秒測試**：只看首屏截圖，寫下三個詞形容它。若出現「乾淨」「現代」「像 SaaS」這類任何網站都適用的詞，辨識度不及格。
3. **逐維度比對**：依 `references/criteria.md` 的三個獎項維度逐項檢視，每項只記「差距」與「證據截圖」，不寫泛用評語。
4. **找唯一的簽名缺口**：判斷這個站最該押注的那一個時刻（hero、某個核心互動、結尾），從主題的素材與語彙裡找，而不是套外面看來的效果。
5. **輸出**：固定三段。「不要動的強項」讓對方知道哪裡別回頭改；「差距」每條附證據與對應維度；「計劃」分 P0（一兩天的瑕疵修正）、P1（簽名體驗重做）、P2（次要頁面沉浸化）、P3（投稿準備）。每個階段的項目要具體到能直接開工。
6. **實作後再跑一次步驟 1**，新舊截圖對照，確認差距真的消失而不是換了另一種通用模板。

## 範例

`references/examples/` 收錄完整審查案例（十秒測試、強項、差距表、計劃與實際取捨、實作後對照）。開始評一個新專案前先讀最接近的一份校準尺度：差距要寫到多具體、計劃要切到多細、哪些提案曾被否決及為什麼。

## 邊界

- 提供一致的評審視角，不是得獎保證；獎項評分方式會變，criteria.md 每條都標注核對日期。
- 評的是渲染後的畫面。設計稿（Figma 等）也可以評，但要先取得截圖，並註明互動與動態尚未驗證。
- 專案本身的技術限制（框架、CSP、無障礙規範、素材授權）由專案文件決定，計劃要在那些限制內提案。

## 何時更新這份 Skill

| 情境 | 更新什麼 |
|------|----------|
| 發現新的通用模板痕跡或評審扣分點 | `references/criteria.md` 的「常見扣分」 |
| 完成一次完整審查與實作 | 新增 `references/examples/<專案>-<年月>.md` |
| 某個提案在實作後被否決或證明無效 | 對應案例的「取捨」段，並視情況回寫 criteria.md |
| 獎項評分方式改版 | `references/criteria.md` 的維度表，標注來源與日期 |
| 審查過程中發現流程多餘或不足 | 本檔「審查流程」 |

更新原則：只收實際審查中驗證過的洞察；SKILL.md 維持精簡，長內容進 references；案例寫法統一，方便跨專案對照。
